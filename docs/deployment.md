# Развёртывание и эксплуатация

Статус: проект, 2026-11-06. Сервер и его действующая конфигурация пока
не обследованы. Приведённые фрагменты поясняют маршрутизацию и не являются
готовым файлом для замены существующего Nginx.

## Топология

Одна машина: существующий reverse proxy, web, worker с дочерним процессом
модели, PostgreSQL и постоянное файловое хранилище. Внешний доступ — только
по HTTPS через `morphemes.mca.nsu.ru`. PostgreSQL и процесс модели наружу
не публикуются; web слушает loopback либо закрытую сеть контейнеров.

Предпочтительная упаковка — Docker Compose с `web`, `worker`, `db`.
Модель запускается дочерним процессом внутри контейнера worker; GPU доступна
только ему, если требуется. Nginx остаётся существующим сервисом машины.
Постоянные тома не зависят от пересборки образов. При невозможности Docker
те же компоненты работают как systemd units с отдельными окружениями.

Начальный ориентир: два лёгких web-процесса и один worker инференса.
RAM, VRAM, число CPU-потоков и размер батча выбираются после измерения модели.
Нужно оставить ресурсы web, PostgreSQL и существующим сервисам машины;
низкое число пользователей не означает низкое потребление памяти моделью.

## Подкаталог `/morphemelab/`

Принято одно правило: Nginx удаляет префикс перед upstream, Django знает
публичный префикс и добавляет его при генерации URL. В `urlpatterns` маршруты
описываются без повторного `morphemelab/`. Эта схема опирается на поведение
[Nginx `proxy_pass`](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)
и [Django `FORCE_SCRIPT_NAME`](https://docs.djangoproject.com/en/5.2/ref/settings/#force-script-name).

Иллюстрация location-блоков внутри существующего HTTPS server:

```nginx
location = /morphemelab {
    return 308 /morphemelab/$is_args$args;
}

location ^~ /morphemelab/static/ {
    alias /srv/morphemelab/static/;
}

location ^~ /morphemelab/ {
    # 10 MiB на файл плюс запас для multipart-обёртки.
    client_max_body_size 12m;
    proxy_pass http://127.0.0.1:8010/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 60s;
}
```

Завершающий `/` в `proxy_pass` существенен: внешний
`/morphemelab/api/v1/projects/` становится `/api/v1/projects/` у upstream.
Заголовок клиентского IP здесь корректен для одного доверенного proxy;
при наличии другого балансировщика цепочку доверия нужно настроить отдельно.

Связанные настройки Django, без секретов:

```python
FORCE_SCRIPT_NAME = "/morphemelab"
STATIC_URL = "/morphemelab/static/"
ALLOWED_HOSTS = ["morphemes.mca.nsu.ru"]
CSRF_TRUSTED_ORIGINS = ["https://morphemes.mca.nsu.ru"]
SESSION_COOKIE_NAME = "morphemelab_sessionid"
CSRF_COOKIE_NAME = "morphemelab_csrftoken"
SESSION_COOKIE_PATH = "/morphemelab/"
CSRF_COOKIE_PATH = "/morphemelab/"
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = "Lax"
CSRF_COOKIE_SECURE = True
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
SECURE_SSL_REDIRECT = True
DEBUG = False
```

Доверять `X-Forwarded-Proto` допустимо только при закрытом от внешних клиентов
upstream и принудительной установке заголовка доверенным proxy. Имена cookies
отдельные, чтобы не пересекаться с другими приложениями домена. Path cookie
не является границей безопасности между приложениями одного origin;
размещение предполагает доверие к соседним приложениям на этом домене.

Ссылки входа/выхода, админка, пагинация, JS-запросы и манифест статических
ресурсов также используют префикс. Сборка Vite формирует ресурсы под
`/morphemelab/static/`; пути из манифеста обрабатываются согласованно
с `STATIC_URL`. Тестовый стенд сразу работает под тем же подкаталогом.

## Файлы и секреты

Предлагаемые каталоги постоянных данных:

```text
/srv/morphemelab/
  static/      # Собранные публичные ресурсы интерфейса.
  uploads/     # Закрытые исходные файлы и отчёты проверки.
  exports/     # Закрытые выгрузки по снимкам.
  models/      # Версионированные доверенные артефакты модели.
  postgres/    # Том данных БД; резервируется средствами PostgreSQL.
```

Загрузки и выгрузки не раздаются через публичный `MEDIA_URL`. Скачивание
проверяет сессию и права, затем использует потоковый ответ приложения
или закрытый `internal` location Nginx. `static/` содержит только ресурсы
интерфейса, не пользовательские данные.

Файл сначала пишется во временный путь, затем атомарно переименовывается
в пределах той же файловой системы. В БД публикуется уже существующий файл.
Осиротевшие временные файлы очищаются после периода ожидания; файлы со
ссылками из БД не удаляются обычной очисткой. Первоначально исходники,
ревизии и опубликованные снимки хранятся до явного решения владельца;
автоматического уничтожения исследовательских данных по сроку нет.

Пароль БД, `SECRET_KEY` и другие секреты находятся вне Git, передаются
через защищённые файлы/переменные окружения. Веса не коммитятся в репозиторий.
Процессы приложения работают без root; каталог моделей для инференса
доступен только на чтение. Приглашения и ссылки сброса не попадают в access
логи или тела журналируемых запросов; страницы их принятия не загружают
сторонние ресурсы и используют `Referrer-Policy: no-referrer`.

Сессии и CSRF используются штатно; ограничиваются попытки входа, принятия
приглашений и загрузки. HTML экранируется, текст слова и комментарии
не вставляются как HTML. Перед выпуском выполняется проверка
`manage.py check --deploy` с production-настройками.
[Официальные рекомендации Django](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

## Наблюдаемость

Структурированные журналы содержат `request_id`, `job_id`, `run_id`,
идентификатор попытки, длительность и код ошибки. Полные входные словари,
пароли и токены в них не пишутся. Журналы ротируются.

Проверяются доступность web/БД, последний heartbeat worker, возраст старейшего
ожидающего задания, число сбоев, свободный диск, RAM и при необходимости VRAM.
Отдельно отслеживается время последней успешной резервной копии.
Внутренние health endpoints доступны локальному мониторингу и не раскрывают
версии/секреты наружу. Отказ модели не делает редактор и сохранение разметки
недоступными. Для запуска достаточно панели состояния в админке и журналов;
канал уведомлений выбирается после знакомства с инфраструктурой владельца.

## Резервное копирование и восстановление

Предложение для начала: ежедневная согласованная копия, хранение 7 ежедневных
и 4 еженедельных копий вне машины сервиса. Целевой RPO — до 24 часов,
целевой RTO — несколько часов; это ориентиры, проверяемые пробным восстановлением.
Экспорт словаря не заменяет резервную копию аккаунтов, истории и запусков.

Для первой версии проще предусмотреть короткое окно обслуживания:

1. Приостановить новые записи web, дождаться текущих транзакций и приостановить
   worker между батчами, не обрывая сохраняемый результат.
2. Сделать `pg_dump` в custom format и копию закрытых файлов, моделей,
   конфигурации и сведений о версиях приложения; сохранить контрольные суммы.
3. Проверить завершение копирования, возобновить сервис и перенести комплект
   на согласованный внешний носитель/сервер с ограниченным доступом.

`pg_dump` даёт согласованный снимок самой БД, но не синхронизирует с ним
пользовательские файлы, поэтому согласованность комплекта обеспечивается
процедурой проекта.
[Документация PostgreSQL о дампах](https://www.postgresql.org/docs/18/backup-dump.html).

Пробное восстановление выполняется до первого рабочего выпуска, затем
регулярно, например раз в квартал: пустая БД, файлы, нужная версия приложения,
проверка хешей, вход, открытие истории, выгрузка и тестовый инференс.
Старая production-копия никогда не восстанавливается поверх рабочей базы
для такого теста. Незавершённые задания после восстановления проходят
обычную процедуру окончания аренды и повторного выполнения.

## Обновление

Собрать и проверить версию, сделать резервную копию, остановить приём новых
изменений и дождаться безопасной остановки worker, выполнить миграции,
обновить web/worker/static, проверить вход и сохранение под префиксом,
возобновить работу. Откат кода возможен только при совместимой схеме;
необратимые миграции требуют заранее подготовленной процедуры восстановления.
Модель обновляется новой записью реестра, прежние веса не подменяются.

Перед реальной установкой нужно узнать ОС, proxy/TLS-конфигурацию, доступные
RAM/CPU/GPU/диск, соседние сервисы, допустимость Docker и место для внешних
резервных копий. Домен и путь известны; доступ к серверу и характеристики
машины пока не предоставлены.
